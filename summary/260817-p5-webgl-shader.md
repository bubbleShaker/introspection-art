# 描画を p5.js の WEBGL + シェーダーに置き換えた

[Issue #9](https://github.com/bubbleShaker/introspection-art/issues/9)

## 何をしたか

Canvas2D で描いていた水面を捨てて、p5.js の WEBGL モード +
自前の GLSL フラグメントシェーダーで描き直した。

音の解析層（`src/audio/`, `src/core/`）と、波紋の減衰の式（`src/scene/ripples.ts`）は
触っていない。置き換えたのは `src/scene/waterScene.ts` 一枚と、その周りだけ。

## いちばん大事な違い

**前**: 空を別のキャンバスに描き、それを 2px のスライスに切って
下半分へ横ずらししながら加算転写していた。CPU が 1 行ずつ絵を平行移動させる方式。

**後**: ピクセルごとに視線を 1 本飛ばし、空へ抜けるか水面に当たるかで色を決める。

```
      ＼      ← 空へ抜ける視線 : skyColor(rd)
       ＼
  目 ●──────── 水平線
       ／＼
      ／  ＼  ← 水面に当たる視線
  ～～～～～～～ 水面 (y = 0)
```

`skyColor(dir)` を空の描画と水面の反射で共用しているのが骨。
反射を別に描き直すのではなく、水面の法線で視線を折り返して同じ空を引く。

## 手作業でやっていたことが、物理から出るようになった

| 前（Canvas2D） | 後（GLSL） |
| --- | --- |
| `depth ** 1.25` などで奥行きを作る | フレネル反射（浅い角度ほど鏡になる）から自動的に出る |
| 短い横線を並べて光の柱を似せる | 月を向いた波面が光り、結果として柱ができる |
| 太線＋細線の重ね描きで滲みを偽装 | 明部抽出 → ぼかし → 加算の本物のブルーム |
| 星は CPU で動かす粒 | 方向から引く。反射にもそのまま乗る |

## 詰まったところ

### 1. p5 は自作シェーダーに `#version` を足さない

p5 2.x は WebGL2 コンテキストを取り、組み込みのシェーダーには
`#version 300 es` を前置する。しかし **`createShader()` に渡したものには手が入らない**。
そのまま GLSL ES 3.00 の書き方（`in` / `out`）をすると
「storage qualifier supported in GLSL ES 3.00 and above only」で落ちる。

自分で、しかも 1 行目に書く。前にコメントすら置けない。

ついでに `sample` は予約語で、変数名に使えない。

### 2. 遠方の水面がちらつく

水平線際は 1 ピクセルに何十もの波が入る。そのまま描くと白い砂嵐になる。

細かい波を距離で消すと止まるが、今度は遠くがただの鏡になって嘘くさい。
**消したぶんの「暴れ」を持ち帰り、月の像を広げる（そのぶん薄める）のに使う**と、
「遠くの月の道はぼんやり滲む」という見え方になった。マイクロファセットの
考え方をそのまま持ってきた形で、この一手が水面の説得力をいちばん上げた。

星も同じ理屈で、暴れている方向では溶けて消えるようにしている。

### 3. 手前に丸い光の塊が出る

水面の暴れ（blur）が手前で 0 になると、たまたま月を正面から返した
ひとつの面が月をまるごと映して、丸い光の玉になる。
実際の水面には必ず目に見えないさざ波があるので、下限を入れた。

### 4. フレームバッファの上下が逆

p5 が板に載せる texCoord は「上が 0」（画像を貼ると正しい向きになる並び）。
一方、フレームバッファをテクスチャとして読むと「下が 0」で入っている。
頂点シェーダーで一度返しておくと、テクスチャを読む側はどれも素直に書ける。

### 5. 画面の位置と水面の位置は比例しない

波紋は画面上の `(x, depth)` で持っている。これを水面上の位置へ直すと、
画面 depth 0.12（水平線際）はワールドでは距離 14 になる。
そこへ落とした波紋は輪が小さすぎて見えなかった。落とす位置を手前へ寄せた。

## 代償

- **バンドル**: 14.4kB (gzip 5.7kB) → 1.2MB (gzip 357kB)。ほぼ全部 p5
- **WebGL2 必須**: 無い環境では絵を描かず、その旨を伝えて音だけ鳴らす
- **GPU 負荷**: フレーム時間の中央値を見て、遅ければ描画の細かさを
  1 段落とす（2 → 1.5 → 1 → 0.75）。一度落としたら戻さない

## レビューで見つかった、自分では気づけなかったこと

- **`redraw()` が async だった。** p5 2.x の `redraw` は Promise を返す。
  シェーダーのコンパイル失敗はそこで reject になるので、拾わないと
  「画面は真っ暗・毎フレーム unhandled rejection・ユーザーには何も伝わらない」
  になる。`isSceneSupported()` は WebGL2 の有無しか見ていないので、
  uniform の本数や精度で落ちる場合はここが唯一の網だった。
  描画側で失敗を捕まえて一度だけ伝え、以降は試さないようにした。

- **負荷判定の閾値を 30fps のすぐ上に置いていた。** 見ているのは
  requestAnimationFrame の間隔であって描画コストではない。省電力モードや
  30Hz の画面では、描画が軽くても 33ms が定常的に出る。何も問題の無い端末が
  数秒で最低画質に落ちて、しかも戻せない設計だった。閾値を離し、
  起動直後のジャンクを避けるウォームアップも入れた。

- **`bloomBuffer` だけ pixelDensity が追従しない。** p5 の Framebuffer は
  大きさを明示すると自動追従から外れるが、外れるのは大きさだけでなく
  **細かさもだった**。画質を落としても滲みだけ元の細かさで走り続け、
  さらに滲みの見かけの太さが段階的に変わっていた。

- **1.02 のオーバースキャンは、テクスチャを読む段では効かない。**
  `gl_FragCoord` から座標を作るシーンの段では無害だが、texCoord で読む
  ブルームと合成の段では、読む位置ごと広がって絵が拡大される。
  シーンの段だけに留めた。

あわせて、p5 に依存しない計算（画面↔水面の座標変換、細かさの段階）を
`camera.ts` / `quality.ts` へ切り出してテストを書いた（20 件）。
とくに `camera.ts` のテストは、**シェーダーが視線を組み立てている式を
TypeScript 側からもう一度解いて突き合わせる**もので、
片方だけ変えて黙ってずれるのを防ぐためにある。
